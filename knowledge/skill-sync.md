# Skill synchronization

For centrally managed, opt-in skill distribution, consult the [canonical manifest](https://github.com/haichi-co/.github/blob/main/.github/skill-sync.json) and [sync workflow](https://github.com/haichi-co/.github/blob/main/.github/workflows/sync-skills.yml). The [engine](https://github.com/haichi-co/.github/blob/main/src/skill-sync.ts) governs synchronization behavior; its tests and TypeScript configuration are verification resources.

## Key facts and constraints

- The v3 manifest defines each skill's source, destination, explicit managed files and unique enrollment topic. Repositories opt into each skill independently through that topic; installing the organization App alone does not enroll them.
- When synchronization is enabled, discovery uses an organization-scoped read-only token; the writer token is restricted to the unique union of discovered target repositories. No targets means no writer token. The engine rechecks repository identity, enrollment and default branch before each write.
- Synchronization creates or updates one reviewable PR per repository-skill pair, never auto-merges, and makes no writes when the default branch or pending PR already matches. Unexpected branch changes fail closed; only manifest-managed files are changed, without executing target code or modifying repository-specific agent instructions, unrelated skills or workflows.
- Removing a topic stops updates for that skill without deleting its existing files or affecting other enrollments. When enabled, the hosted workflow reconciles on relevant main updates, daily at 05:19 UTC, or on manual dispatch, which defaults to a dry run.
- All external Actions used by synchronization and verification, including the App-token action, are pinned to verified full upstream commit SHAs and release comments. Dependency updates follow the reviewed procedure in the root README; token scope and enrollment semantics are unchanged.
- The credential-free `verify` check runs for every PR targeting central `main`; the `sync` job does not run on PRs. PR verification has a separate concurrency group per PR, without entering the writer queue. Push, schedule and manual dispatch are subject to the reviewed authorization policy. Verification runs even when synchronization is disabled. It also validates the separate [repository Admin reconciler](repository-admin-reconciliation.md) and its fixtures without credentials; this does not change skill-sync token scope.

## Why authorization is separate from credentials

- [Decision #38](https://github.com/haichi-co/.github/issues/38) makes the human owner the personal reviewer and reserves central Admin for that owner; `agent-hachi` remains non-admin Maintain here. [#37](https://github.com/haichi-co/.github/issues/37) enforces reviewed main and required CI. A writer can nevertheless execute an unreviewed branch workflow that accesses repository-level Actions secrets. Main protection does not isolate a repository-level App key.
- [#39](https://github.com/haichi-co/.github/issues/39) requires owner-configured `skill-sync` environment: selected deployments, exactly a branch policy for `main`, no tags/wildcards/PR refs; no mandatory deployment reviewers (scheduled sync must run unattended), admin bypass disabled where supported. The existing private key belongs only in that environment, and the public client ID is supplied there and compared to the reviewed identity. No new permissions or credentials. GitHub Free supports these restrictions on this public repository; changing visibility or machine role breaks assumptions.
- [Decision #50](https://github.com/haichi-co/.github/issues/50) selects a reviewed configuration-as-code flag rather than an Actions variable or boolean secret. The merged context can fall back to a repository/organization value when the environment equivalent is absent. Environment variable timing/precedence is documented [here](https://docs.github.com/en/actions/reference/workflows-and-actions/variables#configuration-variable-precedence); [secret precedence](https://docs.github.com/en/actions/reference/security/secrets#naming-your-secrets) has the same fallback concern. A direct [scope-specific environment-variable lookup](https://docs.github.com/en/rest/actions/variables#get-an-environment-variable) requires an unavailable built-in workflow-token permission. Using another privileged token, broadening the App, minting discovery tokens before authorization, or relying on merged contexts for enablement was rejected. An owner-controlled cryptographic nonce was also rejected for additional secret-management overhead. The nonsecret public App ID is pinned in policy: a missing or wrong configured ID fails closed when synchronization is requested; an identical lower-scope fallback does not change identity but is not proof of environment provenance.

## Credential provisioning and recovery decision

- **Why environment-only:** GitHub [holds environment secrets until deployment protection rules pass](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments). A repository-level private key is accessible to same-repository branch workflows without owner review; an organization-level copy accessible to this repo has the same flaw. Neither excluding external contributors nor masking/not printing secrets prevents misuse: code can use a key directly to mint installation tokens with the App's granted permissions, outside the reviewed workflow's read-only discovery and target-restricted writer path. Main review, non-admin machine access and an environment-only key are complementary controls, not alternatives. A broad organization sync was tried and removed in #39; do not recreate it, even as a backup (Free-plan limitations on private repo access do not protect this public repo).
- **Primary provisioning:** Doppler `haichi-co` is the external credential source. Use its [GitHub Actions integration](https://docs.doppler.com/docs/github-actions) with destination repository `haichi-co/.github`, environment `skill-sync`, not the organization or repository-wide secret scope. Sync only the intended skill-sync config; as more credentials are added, keep its synced config narrowly scoped instead of exposing all future project secrets. The stable destination name is `SKILL_SYNC_APP_PRIVATE_KEY`, not a dated key name, so rotation can replace the value without changing workflow code. The three `DOPPLER_*` metadata secrets generated by the integration are not authentication inputs to this workflow. The public `SKILL_SYNC_APP_CLIENT_ID` is an environment variable, and the enable flag belongs solely in reviewed JSON, not in Doppler or Actions variables.
- **Fallback provisioning:** If Doppler sync fails or is unavailable, the owner can securely provision the original PEM from its authorized recovery source directly into the *same* `skill-sync` environment (GitHub UI or an authenticated CLI using standard input, never chat, issues, committed files, command-line arguments or logs). Pause or repair a failing sync if it could overwrite a manually recovered value, and restore the scoped integration after recovery. Verify exact environment rules and names-only secret metadata, ensure no key exists at repo/org scope, and validate via the reviewed dry-run procedure before resuming normal sync. If no trustworthy recovery copy exists, stop for separately authorized App-key rotation/revocation. Redundant provisioning methods improve availability; redundant unprotected access paths defeat the security boundary.
- **No legacy fallback:** Remove repository-level `SKILL_SYNC_APP_PRIVATE_KEY` after the protected replacement is staged and the disabled-run proof passes. Remove repository-level `SKILL_SYNC_APP_CLIENT_ID` and `SKILL_SYNC_ENABLED` as well: these are not sensitive credentials, but retaining alternate definitions obscures the authoritative environment identity and reviewed enable policy. Metadata verification cannot establish the key's validity or prove that a formerly broadly scoped key was never accessed; separately assess and authorize rotation if necessary. The current evidence and acceptance record is #39, not the existence of this document.

## Reviewed execution policy and migration

- The [policy](https://github.com/haichi-co/.github/blob/main/.github/skill-sync-policy.json) is authoritative for enablement. The [guard](https://github.com/haichi-co/.github/blob/main/src/skill-sync-policy.ts) accepts canonical JSON with exact typed booleans `enabled`, `dry_run_only`, and an expected `app_client_id`. Missing, malformed, duplicate/extra fields or unexpected types fail closed. No Actions flag is consulted. Disabled means no App token or sync regardless of lower-scoped values. Enabled dry-run-only permits only manual dispatch with dry_run true; enabled normal mode allows the existing trusted push, schedule and dispatch behavior. The [tests](https://github.com/haichi-co/.github/blob/main/src/skill-sync-policy.test.ts) exercise these invariants, App identity and stale-run rejection.
- The `verify` job runs independently of credentials. Only the canonical repository's main push/schedule/manual dispatch can enter the `sync` job, which declares the protected environment and depends on successful verification. Guard checks repository/ref/event and checkout SHA; a bounded, read-only main-ref API call using the existing contents-read workflow token confirms the run SHA is current. Only then is a positive output available; every App token, discovery and synchronization step requires it. The check is repeated before writer token creation and synchronization. No real key is referenced by PR jobs, nor by guard/test code. Stale reruns are rejected; freshness checks cannot eliminate races with a main update after the check or revoke already minted tokens immediately.
- Source alone does not establish the credential boundary. First reviewed policy is disabled; separately authorized owner stages the restricted environment and existing key/client ID before merge, takes preflight target and run snapshots, then verifies disabled behavior and dummy-only rejection of non-main branch/tag deployments. Legacy repo-level key and both variables must be removed with explicit owner authorization once the replacement is ready, with names-only metadata read-back and no org duplicate. Owner supplies the key securely from its source or approves new-key rotation/revocation; existing secret values cannot be exported. Test dry-run-only under reviewed main, verify token scope and unchanged targets, then switch normal sync on only through reviewed PR and owner approval. See the [README migration procedure](https://github.com/haichi-co/.github/blob/main/README.md#agent-skill-synchronization). Until #39's live evidence is complete, do not claim deployed isolation.
- To disable, merge a reviewed disabled policy. Urgent stop requires separately authorized owner action to cancel active/queued runs and restrict deployment/key access as appropriate; an in-flight run may already have passed its last guard. Recovery must preserve protected main, exact environment rules, key isolation and owner control; never restore unprotected repository secrets. The boundary depends on correct live role/visibility/environment and on uncompromised owner/key; it does not contain an already stolen private key or compromised administrator.

The active implementation and verification record is [#39](https://github.com/haichi-co/.github/issues/39), with approved switch rationale in [#50](https://github.com/haichi-co/.github/issues/50). Live configuration may lag the source; consult those issues and GitHub read-back rather than treating the desired state as evidence of live deployment.
