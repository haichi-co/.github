# Machine-user repository Admin reconciliation

[Task #41](https://github.com/haichi-co/.github/issues/41) reconciles the owner-approved [decision #38](https://github.com/haichi-co/.github/issues/38): the machine member gets effective Admin on active organization repositories, but remains non-admin Maintain on the central `.github`. The [reviewed deployment config](https://github.com/haichi-co/.github/blob/main/.github/repo-admin-reconcile.json), [workflow](https://github.com/haichi-co/.github/blob/main/.github/workflows/reconcile-repo-admin.yml) and [implementation](https://github.com/haichi-co/.github/blob/main/src/repo-admin-reconcile.ts) govern execution. The owner retains exclusive central administration; a live credential or role change requires separate owner authorization.

## Why a dedicated App

- [Decision #57](https://github.com/haichi-co/.github/issues/57) chooses a private, organization-owned GitHub App installed on **all repositories**, including future creations/transfers. A selected-repository installation would exclude central at the credential level, but updating its selection for each new repository defeats automatic enrollment. An owner-operated external reconciler avoids hosting the key here but adds infrastructure and setup. We do not expand the existing skill-sync App, use a broad personal token, or change the organization base role.
- Grant exactly repository Administration: write, Metadata: read and organization Members: read; no webhooks, subscribed events or other permissions. The App key can nevertheless mint a token with Administration on central because the installation includes central. This is a deliberately accepted residual risk, **not** a credential-level exclusion. The reviewed code never requests such a token, and checks each writer's exact permissions and single repository ID before using it. The key and any compromised owner remain powerful outside these controls. See GitHub's [installation token documentation](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app).
- The boundary relies on [central main protection](main-protection.md), machine Maintain/non-owner membership, protected public-repository environment, trusted GitHub-hosted runners and private key isolation. The initial source does not provision a credential or establish live deployment. Do not infer that the environment or exact App API behavior is verified merely from passing fixtures.

## Reviewed deployment and reconciliation

- Configuration is canonical JSON with exact fields and types: `enabled`, `apply_enabled`, organization, central repository, owner and machine login/name and immutable numeric IDs, expected non-admin base permission, and App client/registration/installation IDs. The initial config is disabled with null App bindings. No runtime organization, target, identity or permission overrides. The credential-free authorization job validates repository/ref/event, exact workflow and checkout SHA, current protected main and public central identity before permitting the environment job. A copied enabled config fails closed on mismatched deployment identity.
- `enabled: false` is inert; `enabled: true, apply_enabled: false` allows manual dry-run only; both true permit explicit non-dry-run dispatch. The initial workflow has no schedule; dry run defaults true. A future reviewed daily schedule follows successful live acceptance. There are no PR or reusable-workflow triggers and no checkout of target code. Serialization prevents overlapping runs.
- Validate the private App registration and all-repository installation, exact identities/permissions, active owner and machine memberships and effective central Maintain. Discover with a read-only installation token (Metadata and Members read); require every page, distinct repo IDs/names, consistent owner and counts for public/private inventory. Any visible unexpected base role stops the run; limited App credentials may not expose the exact base role. The owner must verify base Write separately; active non-owner membership and effective central Maintain guard against blanket Admin, not every possible base-role change. Missing inventory counts or inconsistent API responses stop execution rather than broaden credentials.
- Exclude central by immutable ID and every case-insensitive `.github` name; a missing pinned central from this hosted deployment is an error, not permission to proceed. Skip archived/disabled repos without altering them. Already-Admin needs no mutation. Build the entire deterministic plan before minting a writer; dry run never mints one. Each planned grant uses a new token restricted to one non-excluded numeric repository ID, Administration write and Metadata read. Confirm actual token repository inventory and permissions; recheck current main, membership, central and target identity/eligibility/effective role close to the write. Only [add/update collaborator](https://docs.github.com/en/rest/collaborators/collaborators#add-a-repository-collaborator) with `{"permission":"admin"}` is allowed. Require 204 and read back effective Admin. An invitation, unexpected denial/response or read-back failure stops the run; no blind mutation retry, no downgrade or grant to other identities. A second converged pass makes no writes and mints no writer.
- Revoke each issued token when done, including on failure. Bounded GET retries; mutation outcome may be ambiguous, so inspect live state before retrying a failed run. Public logs report counts and controlled errors, not private repository names, API bodies or credentials. Existing verified grants are not automatically rolled back on partial failure. Rechecks narrow but cannot eliminate races between API calls; cancellation/config changes cannot instantly revoke previously issued tokens. No automatic repair of central, org membership, rulesets or base permission.

## Staged provisioning, proof and recovery

1. Merge the disabled source through normal personal owner review and green checks. With separate owner authorization, verify both main rulesets, public visibility, owner and machine roles, exact org base, and existing target state. The [current-state record](https://github.com/haichi-co/.github/issues/41) is authoritative for live progress.
2. Owner creates the dedicated private App with the exact permissions above and all-org-repository installation; record only public IDs. Configure environment `repo-admin-reconcile` in central: selected deployments, exactly branch `main`, no tag or wildcard/PR refs, admin bypass disabled where supported, no mandatory deployment reviewer for eventual unattended operation. Test non-main branch/tag denial with a benign dummy-only probe **before** the real key. Never expose the key to repos the machine administers, repository/org-wide scopes, or skill-sync.
3. Use a separate narrowly synced Doppler config/project containing only the Admin App key, destination **central environment `repo-admin-reconcile`** and stable name `REPO_ADMIN_RECONCILE_PRIVATE_KEY`. A secure owner-direct provision into that same environment is the fallback; no alternate broad secret path. Verify names-only secret metadata and exact environment rules. See [skill-sync rationale](skill-sync.md#credential-provisioning-and-recovery-decision) for why scope matters; keep these two Apps and sync destinations isolated. No key material in chat/issues/config/logs. Existing keys cannot be exported from Actions.
4. Bind the App and installation identities through reviewed JSON, first in dry-run-only mode. Explicitly dispatch reviewed main and verify actual API behavior, total inventory, zero writer mints/writes and unchanged central/base/other permissions. If the narrow token cannot obtain complete evidence, stop and evaluate an alternative; do not grant additional permissions automatically.
5. Separately authorize a controlled disposable active repository grant, verify one expected change and then zero on repeated apply; confirm central and unrelated permissions remain untouched. Only after that evidence, review and enable daily scheduled apply. The scheduler is eventual consistency, not org-wide inheritance; public repository schedules can be delayed/disabled, so use reviewed manual dispatch for recovery.
6. Disable by reviewed config. Urgent stop requires separately authorized owner cancellation of runs and restriction of environment access or suspension of the dedicated installation. Potential exposure requires owner-approved rotation/revocation, not reverting to unprotected secrets; check live grants and audit evidence. Do not automatically remove already granted Admin, change central rules or lower other users' roles.

## Adoption by another organization

The executable reconciler and fixture checks are reusable; installation, credentials and reviewed deployment identities are local to each owner. Cloning, forking or templating the repo does not transplant live App installations, secrets, environment or branch protection. Start disabled/unbound, replace the reviewed organization, repository, owner, machine and App IDs with locally verified values; adapt local main protection/CODEOWNERS, source references and OKF pins before enabling. For this public Free repository, environment branch restrictions are available; private adoption requires verifying equivalent protections on the destination plan, and changing the public-only guard would require a separate reviewed design. Never reuse the Haichi key or installation in another organization. App registration manifests and a repeatable bootstrap procedure may reduce provisioning friction later ([#43](https://github.com/haichi-co/.github/issues/43)); no cross-org installer or repo-wide releases are needed now. Selected-repo/manual or external execution remain possible if another owner requires stronger key-level central exclusion.

Fixture tests prove behavior against modeled responses, not live App capabilities. Record actual deployment and idempotence evidence on #41 before closing it.
